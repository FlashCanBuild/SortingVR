## Gameplay Design: Acting Out Selection Sort
**Goal:** The player "acts out" the algorithm by choosing the correct action at each step. Wrong actions are corrected immediately.
### Decisions so far
- **Wrong action:** the block teleports back to its slot and the player gets a warning. 3 mistakes restarts the algorithm (tentative; may be too punishing, check in usability testing).
- **Compare:** the two blocks being compared are highlighted. The player presses a TRUE or FALSE button to choose which code branch runs. No physical block interaction.
- **Swap:** the player can pick up any block, but can only put down the two blocks that the algorithm swaps at that step.
- **Variables:**
  - Variables set by a decision in the loop body (e.g. `min_idx`) are notched sliders, one notch per index. The value only counts when the player releases the slider.
  - Loop-controlled variables (`i`, `j`) have no sliders. They are read-only indicators the game moves automatically.
### Architecture (leaning toward)
- Skip abstracting loops and conditionals into lambdas... That would mean building an interpreter, and I only have one algorithm to generalize from.
- Instead, model the algorithm as a list of `Step`s (`COMPARE`, `SWAP`, `SET`, ...) generated by running the real algorithm on a copy of the data.
- A referee tracks the current step and strike count, checks player actions, and emits signals. The VR layer (blocks, slider, button) just listens.
- Benefit: the referee can be tested without the headset.

### Open questions
- Do the auto-moved `i` and `j` need their own steps, or can the VR layer infer them (a `COMPARE` step already holds `j`)?
- How does the referee know when to wait for the player and when to advance on its own?
- Slider vs. a token that snaps onto a block's slot (reuses snap zones I'm already building).
- Will the "read-only loop variables" rule hold for `while` loops in other algorithms (insertion, quick sort)?
