## Design decisions

### Gameplay

- The player acts out the algorithm by choosing the correct action at each step. A wrong action teleports the block back to its slot and warns the player. 3 mistakes restarts the algorithm (tentative - check this in usability testing, it may be too punishing).
- **Compare:** the two blocks being compared are highlighted. The player presses TRUE or FALSE to choose which code branch runs. No physical block interaction.
- **Swap:** a physical **temp slot** makes the hidden `temp` variable visible. A swap is decomposed into 3 separate move steps (block to temp, block to its new slot, temp to the other slot), mirroring the pseudocode line for line.
- **Variables:**
    - Index variables are sliders with a notch at every index. The value only counts when the player lets go of the slider.
    - Variables set by a decision in the loop body (e.g. `minIndex`) are player-controlled.
    - Loop-controlled variables (`i`, `j`) are auto-moved, read-only indicators. A setting will let the user choose whether the game auto-moves them.
- **Slot = pointer, block = value.** A block only has a value. A slot holds a reference to its block, or none.

### Architecture

- Rather than abstracting loops and conditionals into lambdas (that would mean building an interpreter), the algorithm is modeled as a list of `Step`s, generated by running the real algorithm on a copy of the data.
- `Step` is a base class with subclasses `CompareStep`, `MoveStep`, and `SetStep`. Every step stores the pseudocode line it belongs to, so the backboard pointer knows where to point.
- `Step.TEMP_SLOT` identifies the temp slot. Variables are identified by `StringName`.
- Each algorithm's pseudocode lives in the same file as its trace builder so the line numbers and text can't drift apart.
- Leaning toward the board script holding the slot references, not the referee, so the referee never touches the 3D scene and can be tested without the headset.

### Open questions (to answer before writing `Referee.gd`)

- What does a player action look like as data? (button answer, block move between slots, slider release)

| Player Action                     | Data                                      |
| --------------------------------- | ----------------------------------------- |
| Button answer `bool`              | `CompareStep(line, slot_a, slot_b, bool)` |
| Block move between slots          | `MoveStep(line, from_slot, to_slot)`      |
| `var` slider release on index `i` | `SetStep(line, var, i, is_loop`           |

- What signals does the referee emit? (what do the board and the info panel each need to hear?)
	- `step_advanced()` -> tells the board to show the next step, tells the info panel to move loop-controlled variables
	- `mistake_made()` -> tells the info panel to increment mistakes and reset blocks to the previous positions
	- `finished()` -> tells the info panel and board that the algorithm is done
	- Perhaps other signals later... 
- How does the referee treat narrated steps vs. player-required steps, given the auto-move setting?
	- The referee should jump to the next line that requires player input (aka the next Step in the referee's internal "answer sheet")
- What happens when a `SetStep` target already matches the slider's current value? Where does each slider start?
	- You'd hold it and then release it at the same spot? Or maybe we ignore that Step - we can make a check whenever adding a SetStep in the Referee that if it doesn't change anything, we ignore the step?
	- Each slider should have an `undefined` start position to begin at the leftmost position. Say the index is `-1` to mean undefined. Once it's defined (e.g. `int i = 0`), we can move it from `undefined` to `0`.
	- However, if a variable goes out of scope (like `j` at the end of an iteration of the outer loop), it should automatically go back to `undefined`, or `-1`. We don't want the user to have to perform any action that isn't explicitly on the pseudocode.
- Should the progress bar count narrated steps?
	- No - the progress bar is player-facing.
- How will the board and sort selector get the trace and pseudocode for whichever algorithm is selected? (maybe an abstract base class)
	- We should have an abstract base class holding a few things:
	- A constant `PSEUDOCODE` array of strings
	- A `build` function that takes an array of `int`s and generates an array of Steps
	- A list of all named variables it needs (e.g. `i`, `j`, `minIndex`, etc.)
		- In fact maybe we want a tiny class Variable which has a string and a `isLoopControlled` flag?
